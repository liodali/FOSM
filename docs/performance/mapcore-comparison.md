# MapCore / FOSM smoothness analysis

Inspected 2026-10-18. Static source analysis only; no native-versus-Flutter device benchmark was run for this review. No rendering or package code was changed.

The strongest transferable design is a retained map scene: camera motion reuses loaded textures and geometry, background work prepares replacements, and graphics setup is paced separately. FOSM already uses Flutter's GPU renderer; switching from Dart to C++ alone does not establish a performance win. The likely opportunities are reducing UI-isolate work during motion and making tile replacement visually continuous.

## Source identity

The wrapper manifest requires `liodali/maps-core` `4.0.1-spm.2`. The root package lock and `.build/checkouts/maps-core` still identify `spm.1` (`e04be5b5`). The iOS workspace/example lock and inspected DerivedData checkout identify `spm.2` (`62ca9960`). The macOS example lock is also `spm.1`.

A local diff of those two commits changes only `ios/graphics/Texture/TextureHolder.swift`: explicit RGBA normalization for indexed PNGs on macOS. The camera, scheduling, and rendering findings therefore apply to both inspected revisions. Dependency versions should be aligned before comparing built binaries.

## Differences that still matter in FOSM

1. **Motion and tile-grid demand are coupled.** `TileManager.calculate()` has an unchanged-camera fast path, but any change in center or fractional zoom invalidates it. It rebuilds tile slots/jobs, prunes queues, and pumps loads. This also happens when a small move has not changed tile membership. Pinch calls the zoom path and `setState`; normal camera motion rebuilds the map subtree. Evidence: [TileManager.calculate](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/api/tile_manager.dart:691), [fractional pinch](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/view/map_view.dart:1770).

   Candidate: maintain a cheap camera transform each display frame; reconcile tile demand only when tile membership, selected source zoom, viewport, or padding requirements change. Re-rank queued work when needed without rebuilding every tile descriptor. Coalesce multiple input updates within one frame while preserving cumulative pinch scale and focal-point math. Use focused invalidation for tiles, markers, labels, and controls. RepaintBoundary alone does not eliminate build/layout work.

2. **Work is bounded per job, not by one shared frame deadline.** FOSM already parses MVT off-thread, has stale-work gates, runs a time-sliced vector renderer, and prepares labels separately. The vector default permits three concurrent decode jobs, each with an 8 ms cooperative rendering interval; label preparation has its own 4 ms interval. These are not guarantees that total UI work fits a frame, particularly at 120 Hz (8.33 ms total frame interval). Async Dart tasks share the UI isolate for Canvas/style/text work. Evidence: [decode admission](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/vector/render/vector_tile_runtime.dart:163), [vector render budget](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/vector/render/vector_tile_renderer.dart:75), [label budget](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/vector/render/label_overlay.dart:220).

   Candidate: a shared, frame-aware admission budget for all UI-side tile rendering, label preparation, and publication work. Measure remaining time and defer nonessential work during interaction; do not merely lower every independent timer. Keep parsing/background work separate, bound simultaneous `toImage` submissions, and trace long indivisible operations. Avoid starving visible coverage while prioritizing input.

3. **Vector geometry is rasterized into tile images.** FOSM evaluates styles, builds Canvas paths, records a Picture, and calls `toImage(256, 256)`. It reuses these images during motion, but newly selected logical zooms still require this pipeline. MapCore can retain vector geometry buffers and update draw-time matrices/styles rather than flattening all base vector content into tile images. Evidence: [vector image creation](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/vector/render/vector_tile_runtime.dart:459), [Quad2d.swift](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/DerivedData/OSMFlutterFramework/SourcePackages/checkouts/maps-core/ios/graphics/Model/Quad/Quad2d.swift:137).

   Candidate: first measure cold vector tile render and image-publication cost. Consider retained Pictures or prepared geometry only as a measured prototype: they trade image-generation cost for per-frame replay cost and can affect memory, line widths, labels, and clipping. A full native backend is a separate architectural choice.

4. **Fallback coverage has different lifetime rules.** FOSM retains a grid snapshot during fractional source-zoom changes and releases it when the new viewport is ready or the timeout fires. MapCore retains/masks individual fallback tiles until coverage is replaced. Evidence: [fractional snapshot lifetime](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/view/map_view.dart:1109), [Tiled2dMapSourceImpl.h](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/DerivedData/OSMFlutterFramework/SourcePackages/checkouts/maps-core/shared/public/Tiled2dMapSourceImpl.h:470).

   Candidate: geographic parent/child fallback coverage with per-region replacement, reusing cached images as the map continues moving. Release obsolete regions promptly under a memory budget; handle transparent tiles, clipping, disposal, and fast zoom reversal. This improves perceived loading continuity even when network latency stays unchanged.

5. **Markers still have per-marker projection and widget layout costs.** FOSM culls offscreen markers before building their contents, but iterates the collection and projects each marker. Visible markers use Positioned widgets; clustering adds its own work. This matches the existing offline iPhone measurements, where UI costs are much greater than raster costs. Evidence: [marker iteration/projection](/Users/dalihamza/Desktop/FlutterApps/FOSM/lib/src/view/marker_layer.dart:274), [saved iPhone results](/Users/dalihamza/Desktop/FlutterApps/FOSM/docs/performance/results-ios.md:9).

   Candidate: index markers geographically, query an expanded viewport, cache projected world coordinates, and add an optional atlas/Canvas path for many simple pins. Keep arbitrary widget markers available for rich interactive content. Preserve semantics, hit testing, anchor behavior, clustering, and fixed screen size at fractional zoom.

## Native code is not a performance oracle

The inspected native code also has costs worth profiling:

- `MCMapView.draw` waits for a render slot and uses `waitUntilScheduled()` during onscreen presentation. GPU backpressure can block the drawing thread; replacing this requires measuring latency and drawable synchronization, not removing waits blindly.
- The 6 ms graphics-task allowance leaves little room in an 8.33 ms frame interval. The thread pool sizes itself from hardware concurrency; its general work queue consumes FIFO entries. Neither guarantees optimal workload scheduling.
- The wrapper prints raster tile URLs; suppress this outside diagnostics. Its `layoutSubviews` assigns the child's frame from the parent's `frame` instead of local `bounds`; this is a layout correctness concern, not an established jank cause. Marker updates search arrays and remove/re-add graphics icons, which deserves measurement for frequently moving markers.
- The Swift wrapper forwards camera bounds changes directly to its delegate. A Flutter bridge should avoid sending heavy state updates back through Dart on every event unless needed; keep native gesture/camera processing local and batch observational events.

Evidence: [MCMapView.swift](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/DerivedData/OSMFlutterFramework/SourcePackages/checkouts/maps-core/ios/maps/MCMapView.swift:320), [graphics-task budget](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/DerivedData/OSMFlutterFramework/SourcePackages/checkouts/maps-core/shared/src/map/scheduling/ThreadPoolSchedulerImpl.cpp:197), [worker scheduling](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/DerivedData/OSMFlutterFramework/SourcePackages/checkouts/maps-core/shared/src/map/scheduling/ThreadPoolSchedulerImpl.cpp:43), [tile URL logging](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/Sources/OSMFlutterFramework/OSMTileConfiguration.swift:47), [wrapper layout](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/Sources/OSMFlutterFramework/OSMView.swift:216), [marker updates](/Users/dalihamza/Desktop/SwiftApps/OSMFlutterFramework/Sources/OSMFlutterFramework/models/MarkerManager.swift:54).

## Proposed order

1. **Measure the missing workload first.** Existing saved iPhone results are short, generated offline-raster runs at 60 Hz. They do not measure production vector cold loads or network latency. Instrument fetch, parse, style/path recording, image generation, publication, label layout, grid reconciliation, marker work, and frame build/raster timings. Compare the same device, viewport, camera trajectory, zoom range, style, cache state, and refresh rate. Capture cold and warm raster/vector runs, pinch reversals, fling while tiles arrive, and longer repeated sessions. Native signposts/Metal captures complement Flutter timelines; cross-stack latency needs an input-to-present measurement.
2. **Decouple camera motion from grid reconciliation and map-wide rebuilding.** This is the clearest immediate optimization supported by source inspection. Validate event coalescing, tile-boundary changes, focal invariance, bounds, and interrupted animations.
3. **Introduce shared frame pacing for tile/label work.** Judge it by lower frame-tail latency while keeping visible coverage time acceptable; reducing tile throughput alone is not success.
4. **Add per-region fallback coverage.** Measure blank/checkerboard area over time and time to sharp coverage under constrained loading, plus image memory during rapid reversals.
5. **Optimize large marker sets where needed.** Index first; prototype batched simple pins as an opt-in path.
6. **Evaluate the native backend only after an equivalent benchmark.** Embedding the existing MCMapView on iOS could retain camera/render ownership in MapCore, but requires deliberate API, marker, gesture, lifecycle, Flutter composition, and Android/web parity work. Do not start a C++ rewrite solely from these source findings.

Acceptance should consider UI/raster p95 and p99, missed frames at the actual refresh rate, worst interaction stalls, input latency, visible/sharp coverage latency, wasted/stale work, network volume, and peak/steady memory. The current results establish neither a native performance ratio nor a guaranteed improvement from any candidate above.
